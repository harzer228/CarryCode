# flashGPT

flashGPT — переносимое меню для OpenAI Codex CLI и OpenCode CLI. Оба клиента запускаются локально и выполняют команды на компьютере, к которому подключена флешка. Модель работает у выбранного облачного провайдера. Флешка хранит бинарники, настройки, сохранённый вход и историю сессий. Для облачной сессии нужны загруженная ОС, доступ в интернет и действующий аккаунт провайдера.

## Что войдёт в v0.1

- Одна флешка exFAT для Windows 11, Ubuntu 24.04 LTS и актуального Arch Linux со штатным ядром `linux`. Первый релиз рассчитан на x86-64. На обеих Linux-системах ручной запуск доступен из терминала, включая TTY, а автооткрытие проверяется в GNOME.
- Двойной щелчок по `flashGPT.exe` на Windows. Запуск `./flashgpt` из терминала в каталоге флешки на Ubuntu и Arch. Ручной запуск использует готовые бинарники из архива. В README описаны необходимые права на выполнение и проверка параметров монтирования, если ОС блокирует запуск с носителя.
- Автооткрытие окна на каждом компьютере, где пользователь однажды включил эту функцию. Фоновый помощник работает в его графической сессии, распознаёт зарегистрированную флешку и открывает только меню. На неподготовленном компьютере используется ручной запуск. Windows не запускает обычные USB-накопители через AutoRun. [Microsoft](https://www.microsoft.com/en-us/msrc/blog/2009/04/autorun-changes-in-windows-7/)
- Один зашифрованный профиль на флешке. При первом запуске пользователь задаёт пароль и входит в Codex через ChatGPT или ключ OpenAI API. Провайдер OpenCode подключается отдельно через доступный ему способ входа. Дальше достаточно разблокировать профиль. При отзыве или истечении входа приложение предлагает повторный вход для соответствующего CLI. [Вход в Codex](https://learn.chatgpt.com/docs/auth) · [Вход в OpenCode](https://opencode.ai/docs/cli/providers/)

## Как выглядит обычный запуск

1. Подключаешь флешку. На подготовленном ПК открывается окно. На новом открываешь его вручную.
2. Выбираешь `Codex CLI`, `OpenCode CLI`, `Проверить подключение и окружение` или `Выйти`. Локальная проверка работает без пароля и доступа к облачной модели. Она проверяет носитель, доступность рабочей папки, свободное место и целостность комплекта. Отдельная проверка соединения помогает отличить проблему DNS, HTTPS или прокси от проблемы входа.
3. Для запуска агента вводишь пароль профиля. Выбираешь папку на компьютере и режим `Диагностика` или `Исправление`. Меню показывает выбранную папку и провайдера. Для общесистемной проблемы можно выбрать отдельную рабочую папку для отчёта и дать агенту контекст по конкретной проблеме.
4. Открывается родной терминальный интерфейс CLI. Ты описываешь проблему, смотришь вывод и подтверждаешь команды или изменения, требующие разрешения. Модель получает запрос и те данные, которые клиент отправляет ей в контексте диагностики.
5. После выхода из CLI меню сохраняет обновлённый профиль. После закрытия временных файлов и успешной записи показывает, что флешку можно безопасно извлечь средствами ОС.

## Устройство проекта

### Лаунчер и файлы на флешке

Весь собственный код flashGPT пишется на Rust, включая меню, управление профилем, `doctor`, запуск CLI, помощника автооткрытия и утилиту сборки релиза. Один нативный бинарник на платформу обслуживает ручной и автоматический запуск. Базовому меню достаточно `std::io`. Дочерний CLI запускается через `std::process::Command` по абсолютному пути с отдельными аргументами и наследует интерактивный терминал. Лаунчер определяет корень флешки по своему пути и проверяет маркер `flashgpt.json`. Для путей с пробелами и кириллицей используются `PathBuf` и `OsStr`.

Комплект использует официальные бинарники клиентов. Codex CLI уже написан на Rust. OpenCode v2 подключается как отдельный штатный бинарник со встроенным Bun. Одна сборка `linux-amd64` содержит общий набор для Ubuntu и Arch. [Исходники Codex](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/Cargo.toml) · [Сборка OpenCode](https://github.com/anomalyco/opencode/blob/v2.2.5/packages/cli/script/build.ts)

```text
flashGPT/
  flashGPT.exe
  flashgpt                       # нативный лаунчер для Ubuntu и Arch
  flashgpt.json                  # версия формата и ID комплекта
  bin/
    windows-amd64/              # полные пакеты Codex и OpenCode
    linux-amd64/                # полные пакеты Codex и OpenCode
  manifests/runtime.json        # версии, относительные пути, SHA-256
  profile/                      # зашифрованные снимки, создаются при настройке
  licenses/
  README.md
```

В репозитории будут `Cargo.toml`, `Cargo.lock`, `src/` с модулями меню, профиля, запуска CLI и автооткрытия, `xtask/` с Rust-утилитой упаковки, а также `docs/` и `.github/workflows/`. Платформенные вызовы изолированы в модулях Windows и Linux. `doctor` проверяет текущую платформу, доступность бинарников и рабочего каталога, права на запись профиля, место, TTY и DNS/HTTPS до выбранного провайдера. На Linux он также проверяет точку монтирования exFAT, возможность выполнения бинарников и доступность штатной песочницы Codex. Вывод не содержит токенов, диалогов или значений секретных переменных. В офлайне меню и локальные проверки доступны, а CLI сообщает о недоступности провайдера.

Меню открывается до чтения больших архивов, разблокировки профиля и сетевых проверок. После выбора клиента проверяются файлы именно его комплекта. На физической флешке отдельно замеряем время до первого кадра меню, от ввода пароля до готовности CLI и от отправки запроса до первого ответа. Это позволяет увидеть задержки монтирования, проверки файлов, запуска клиента и облака по отдельности. Стоимость парольного шифрования сохраняем независимо от замеров.

Первый вход через `codex login`, с device code там, где он доступен. | Браузерный вход, обновление токена и перенос между Windows, Ubuntu и Arch. | OpenCode CLI v2 | `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` указывают во временный каталог. Сессия использует `--standalone`. Вход настраивается штатным `/connect`. В зашифрованный снимок входит согласованная SQLite-база с историей и входом. | `opencode debug paths` на всех трёх системах, пути сервера и базы внутри профиля, завершение приватного сервера, обновление входа и перенос базы. Лаунчер задаёт переменные пути и авторизации только дочерним процессам. Он фильтрует унаследованные переменные, которые могли бы подменить провайдера, токен, каталог данных или сервер. Каждый CLI получает отдельные временные директории, в том числе для кэша. Управляемые настройки ОС и CLI имеют штатный приоритет. Сквозной тест на машине с локальными установками проверяет, что клиенты используют именно профиль флешки. Старые диалоги могут содержать абсолютные пути. При переносе выбираешь рабочую папку заново. Возможность продолжить старый диалог из другого каталога зависит от клиента.

### Защита профиля и восстановление

- Постоянное хранилище — зашифрованный архив `age` с парольным шифрованием через scrypt. Пароль читается без отображения и остаётся в памяти процесса до выхода из меню. В аргументы запуска, переменные окружения и логи пароль не передаётся. Используем Rust-библиотеку `age` со стандартным форматом и потоковой обработкой профиля. [Документация age](https://docs.rs/age/latest/age/)
- После разблокировки лаунчер распаковывает разрешённые файлы в приватный временный каталог текущего пользователя на ПК. На Linux при наличии подходит `$XDG_RUNTIME_DIR`, на Windows используется временный каталог с проверяемыми ACL. Настройки, токены и история возвращаются на флешку после выхода из CLI. Снимок содержит только разрешённые файлы профиля. Кэши, сокеты и служебные файлы песочниц создаются для текущего компьютера.
- Один активный сеанс на профиль. Блокировка на время работы и проверка версии снимка перед записью защищают от двух открытых меню, быстрого переподключения и сохранения поверх более свежего профиля. Лаунчер ждёт завершения CLI и его приватного сервера. Для SQLite проверяется согласованность снимка, включая завершённые записи WAL, если они ещё есть. Распаковщик принимает только относительные пути из ожидаемой структуры и ограничивает размер файлов. [SQLite WAL](https://sqlite.org/wal.html)
- Новая версия пишется во временный зашифрованный файл на той же флешке. После закрытия и синхронизации запись проверяется чтением. До успешной проверки остаётся предыдущий рабочий снимок. При повреждении свежего снимка меню явно предлагает открыть предыдущий. При извлечении во время работы сохранение можно повторить после подключения той же флешки. До успешной синхронизации меню не подтверждает, что профиль сохранён.
- На штатном выходе временные файлы удаляются. После аварийного завершения на компьютере могут остаться расшифрованные данные. При следующем запуске меню обнаруживает такой каталог и предлагает его удалить или восстановить сессию сохранения для той же ревизии профиля. Шифрование защищает отключённую флешку. Компьютер, на котором профиль открыт, должен быть доверенным. Если потерян пароль, понадобится заново создать профиль и авторизоваться.

### Автооткрытие меню

Включается отдельной командой `flashgpt autostart install`, которая показывает, что будет установлено, и регистрирует только выбранный носитель. `flashgpt autostart status` показывает регистрацию, `uninstall` удаляет помощник и его запись автозапуска. На ПК остаётся только локальная настройка распознавания носителя и копия помощника. Пароль и настройки провайдеров хранятся в профиле.

- **Windows.** Помощник запускается при входе текущего пользователя через `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` и получает `WM_DEVICECHANGE`. Дожидается доступной буквы диска и сопоставляет ID тома и маркер комплекта с регистрацией. Открывает собственную локальную копию меню в текущей пользовательской сессии. [События устройства](https://learn.microsoft.com/en-us/windows/win32/devio/wm-devicechange) · [Ключи Run](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys)
- **Ubuntu и Arch с GNOME.** Помощник стартует через пользовательский XDG Autostart. Следит через UDisks2 за появлением точки монтирования, сверяет UUID тома и маркер комплекта и открывает терминал в графической сессии. Для открытия окна сразу после подключения нужны работающий UDisks2, автоматическое монтирование флешки в GNOME и поддерживаемый эмулятор терминала. На минимальном Arch пользователь может смонтировать флешку и запустить меню вручную в TTY. [XDG Autostart](https://specifications.freedesktop.org/autostart/latest/) · [UDisks2 MountPoints](https://storaged.org/udisks/docs/gdbus-org.freedesktop.UDisks2.Filesystem.html) · [UDisks2 в Arch](https://archlinux.org/packages/extra/x86_64/udisks2/)
- Одно открытие на одно подключение. Помощник обрабатывает уже подключённую флешку при входе, игнорирует незарегистрированные тома и сбрасывает состояние при извлечении. Лаунчер сверяет бинарники и их помощники с хэшами, встроенными при сборке. При автооткрытии выбранный CLI запускается после выбора пользователем из приватного каталога текущего сеанса, куда копируются и проверяются только файлы релиза из списка. При обновлении комплекта обновляется и локальная копия помощника из проверенного релиза.

### Режимы агента

| Режим | Codex | OpenCode |
| --- | --- | --- |
| Диагностика | Штатный режим `read-only` с `--ask-for-approval never`. | Встроенные чтение и поиск в пределах рабочей папки и её Git-проекта. Глобальная политика блокирует запись, оболочку и доступ за пределами проекта. |
| Исправление | `workspace-write` с `on-request`. Изменения внутри выбранной рабочей папки допускаются согласно песочнице. Выход за её пределы обрабатывается через штатные разрешения. | Подтверждение команд оболочки и изменений через разрешения V2. За внешние каталоги отвечает отдельное правило. Команда, которую ты разрешил, выполняется с правами твоего пользователя. |

Проверить на чистом ПК эффективные правила, включая конфликт с проектной настройкой. В диагностике автоматическая подгрузка плагинов, MCP и хуков из неизвестного проекта отключается поддерживаемыми настройками или штатным механизмом доверия. Если режим конкретной версии CLI не удаётся обеспечить, меню объясняет ограничение. Если ОС требует UAC или `sudo` для системного изменения, агент показывает предлагаемое действие, а пользователь выполняет его с нужными правами. В первом релизе достаточно проверить диагностику и исправление обычной проблемы в выделенной папке. [Песочница Codex на Windows](https://learn.chatgpt.com/docs/windows/windows-sandbox) · [Разрешения OpenCode](https://opencode.ai/docs/permissions/) · [Приоритет политики OpenCode](https://opencode.ai/docs/policies/#precedence)

На Ubuntu и Arch `doctor` пробует выполнить безопасную команду в штатной песочнице Codex из поставки. Это проверяет работоспособность `bwrap` и seccomp с текущими настройками ядра. Если песочница недоступна, `doctor` показывает ошибку проверки и выявленные ограничения хоста. [Песочница Codex на Linux](https://learn.chatgpt.com/docs/agent-approvals-security#os-level-sandbox)

## Сборка и GitHub

1. Зафиксировать версии и SHA-256 официальных архивов в `runtimes.lock.json`. Кандидаты на первый прогон — Codex `0.167.1` с полным пакетом и OpenCode `2.2.5` с x64 baseline. Окончательные версии закрепляются по результатам прогона. Для Codex берём полную поставку с платформенными помощниками. [Архивы Codex](https://github.com/openai/codex/releases/expanded_assets/rust-v0.167.1) · [Архивы OpenCode](https://github.com/anomalyco/opencode/releases/expanded_assets/v2.2.5)
2. Rust-утилита `xtask` скачивает архивы с официальных URL, проверяет хэши и упаковывает комплект. `cargo build --release --locked` собирает лаунчер для Windows на Windows, а общий Linux-бинарник — на Ubuntu 24.04. Запуск тех же Linux-файлов проверяется на Arch. На флешку распаковывается один `flashgpt-usb-amd64.zip`. Инструкция по обновлению описывает замену файлов приложения с сохранением `profile/` и ID комплекта. Перед миграцией сохраняется предыдущий снимок для возврата к прежней версии. [Cargo](https://doc.rust-lang.org/cargo/commands/cargo-build.html)
3. GitHub Actions гоняет `cargo test --locked` и проверки запуска для Windows, Ubuntu 24.04 и актуального Arch. Для Arch проверка в официальном контейнере покрывает запуск готовых бинарников и работу с профилем. Подключение USB, песочницу Codex и автооткрытие в GNOME проверяем на полноценной системе. В отчёте релиза фиксируем дату и версию ядра проверенного Arch. По тегу CI собирает архив, `SHA256SUMS` и список версий. Перед выпуском проверяется комплект лицензий и уведомлений вложенных компонентов. Для собственного кода предлагается MIT. [Образ Arch Linux](https://hub.docker.com/_/archlinux) · [Лицензия Codex](https://github.com/openai/codex/blob/rust-v0.167.1/LICENSE) · [Лицензия OpenCode](https://github.com/anomalyco/opencode/blob/v2.2.5/LICENSE)
4. В репозиторий идут исходники, воспроизводимая сборка, примеры конфигов без секретов и инструкция на русском с английским кратким стартом. Релиз собирается по списку известных путей. `profile/`, временные каталоги, логи, `auth.json`, реальные SQLite-базы и файлы `.env` исключены из Git и сборки. `README` описывает подготовку exFAT без обязательного форматирования, типы входа, автооткрытие и удаление помощника, сетевые ограничения и восстановление профиля. `SECURITY.md` описывает обращение с утерянной флешкой и канал для сообщений об уязвимостях.

## Порядок реализации и приёмка

1. **Проверить переносимость обоих клиентов.** Распаковать полные релизы, проверить `--help`, песочницу Codex, `opencode debug paths` и работу приватных серверов на Windows 11, Ubuntu 24.04 и Arch. На Ubuntu и Arch запускать одни и те же Linux-бинарники. Временно перенаправить профиль и убедиться, что существующие пользовательские установки не влияют на сессию.
2. **Собрать ручной сценарий.** Меню, выбор папки, запуск каждого TUI, `doctor`, диагностика и исправление. Тестовая задача в отдельной папке сначала объясняет ошибочную настройку. После переключения режима агент вносит согласованную правку и проверяет результат. Тесты также проверяют отказ в изменении в режиме диагностики.
3. **Добавить пароль и перенос входа.** Один раз авторизоваться в обоих CLI на Windows, затем перенести ту же физическую флешку на Ubuntu, Arch и обратно на Windows. После ввода пароля каждый CLI на каждом ПК выполняет короткий облачный запрос с сохранённым входом. Проверить сохранение настроек, отсутствие открытых секретов на флешке, первый вход, неправильный пароль, истёкший вход, прерванную запись и восстановление предыдущей версии. CI использует искусственные профили. Реальный вход проверяется вручную тестовой учётной записью.
4. **Добавить автооткрытие.** На Windows 11 и в GNOME на Ubuntu и Arch пройти установку, повторное подключение, вход с уже подключённой флешкой и удаление помощника. Проверить, что открывается ровно одно окно, чужая флешка игнорируется, а агент ждёт выбора и пароля. На Arch без графического сеанса проверить ручной запуск в TTY.
5. **Прогнать релиз на чистых системах.** Проверить диск с другой буквой и точкой монтирования, каталог с пробелами и кириллицей, отсутствие локального CLI, отсутствие сети, запрет на выполнение, повреждённый архив, заполненную флешку и извлечение во время сохранения. Проверить документацию по опубликованному архиву на новой флешке. Критерий релиза — комплект воспроизводимо собирается из чистого клона и оба агента реально запускаются с одной флешки на заявленных ОС.

План составлен по документации и исходникам клиентов. Испытания с одной флешкой на Windows 11, Ubuntu и Arch ещё предстоят. Главные вопросы проверки — сохранённый вход после смены системы, работа штатных песочниц и корректное завершение OpenCode перед сохранением его базы.
